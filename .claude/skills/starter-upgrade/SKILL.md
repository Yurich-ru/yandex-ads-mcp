# /starter-upgrade

Template-репозиторий копируется один раз. Всё, что улучшили в стартере после этого,
до существующих проектов само не доедет. Этот скилл — обратный поток.

Граница «что принадлежит шаблону» — в `STARTER_MANIFEST` **нового** стартера
(граница может меняться, решает свежая версия):

| категория | что делать при обновлении |
|---|---|
| `template` | заменить файл целиком |
| `once` | не трогать: скопировано при инициализации, дальше живёт в проекте или удалено |
| `mixed` | показать diff, применить **по разделам вручную** — там есть проектное |
| `project` | не трогать никогда |

## Порядок

1. Снять сверку:

   ```bash
   python3 .agents/skills/starter-upgrade/scripts/starter-diff.py
   ```

   Скрипт клонирует актуальный стартер во временный каталог, читает его манифест
   и печатает сводку и diff. Ничего не применяет. Уже склонирован — `--starter DIR`.

   В конце сводки — блок «Предупреждения» (если есть что): symlink в репозитории
   (Portainer не задеплоит); разошедшиеся зеркала скиллов; `.gitignore`, закрывающий
   зеркала; `claude.md` строчными; следы другого фреймворка; проектный `CLAUDE.md`
   с содержимым. Это грабли прогона по существующим проектам, разбор — в разделе ниже.

2. Показать пользователю сводку **до** правок: что новое, что изменилось, что `mixed`.
   Не применять молча — в `mixed`-файлах есть ручные правки проекта.

3. `template`-файлы — скопировать из стартера целиком. Зеркала скиллов
   (`.claude/skills/<name>`, `.codex/…`, `.cursor/…`) — такие же template-файлы:
   **копировать содержимое**, symlink не создавать. Если в проекте они ещё symlink —
   удалить и положить копии.

   Проектные скиллы, которых нет в стартере, зеркалить тем же скриптом:

   ```bash
   python3 .agents/skills/starter-upgrade/scripts/sync-skill-mirrors.py
   python3 .agents/skills/starter-upgrade/scripts/sync-skill-mirrors.py --check   # проверка
   ```

4. `mixed`-файлы — по разделам. В `AGENTS.md` **не трогать «Описание проекта»**; служебные
   разделы (принципы, память, чек-листы) заменять на версию стартера, если проект их не
   правил осознанно; правил — оставить проектную версию и сказать об этом. В `index.md`
   добавить новые записи стартера, проектные не убирать. В `.gitignore`, `.cursorignore`,
   `deploy.yml` — только добавлять строки стартера, свои не удалять.

5. Записать новую версию в `STARTER_VERSION` проекта.

6. Обновить `agent_docs/snapshot.md`: строка «обновлён стартер до X, применено: …,
   отложено вручную: …». Если что-то из `mixed` намеренно не применено — в «Не проверено»
   или «Тупики», чтобы следующая сессия не переприменяла.

7. Прогнать `markdownlint` (в стартере есть workflow) и тесты проекта, если есть.

## Проект без стартера или на другом фреймворке

Правила проверены прогоном по шести проектам (02.09.2026). Инициализация отличается от
обновления: в проекте нет ни `STARTER_VERSION`, ни половины файлов.

### `once`-файлы: инициализация против обновления

- Файла **никогда не было** в проекте (`snapshot.md`, `backlog.md`, `invariants.md`,
  `glossary.md`, `guides/operations.md`, `setup-checklist.md`, `markdownlint.yml`) —
  создать из стартера: это инициализация, а не «возврат удалённого».
- Файл **есть** — не трогать, даже если в шаблоне он изменился.
- `.gitignore` и `.github/workflows/deploy.yml` — не трогать никогда, ни при инициализации.
  Там проектная сборка и проектные исключения, шаблонная заготовка их затрёт.

`setup-checklist.md` оставить с отметками пройденного, не удалять за пользователя.

### Проектный `CLAUDE.md` с содержимым

Не заменять на `@AGENTS.md` сразу — сначала перенести:

1. Всё содержимое `CLAUDE.md` → в `AGENTS.md`, раздел `## Правила проекта`, сразу после
   «Описания проекта» (заголовки внутри понизить на уровень, чтобы вложились в раздел).
2. Проверить построчно, что ничего не потеряно: сверить с исходником, а не «на глаз».
3. Только после этого `CLAUDE.md` = `@AGENTS.md`.

`claude.md` строчными (дубль на case-insensitive ФС): содержимое — указатель, значит
`git mv claude.md CLAUDE.md`; есть текст — сначала перенос по шагам выше.

### Другой фреймворк или старый стартер

Встречалось: alexeykrol v5 (`.claude/SNAPSHOT.md`, `.claude/BACKLOG.md`, свои хуки в
`settings.json`), старый стартер с `docs/` (~90 файлов, однофайловые `adr.md` и
`development-history.md`).

- Накатывать стартер **поверх**. Чужое состояние не сливать и не удалять — это решение
  пользователя, а не побочный эффект обновления.
- `agent_docs/` — память стартера; на чужие хранилища поставить **указатели** из
  `agent_docs/index.md`, а не копировать содержимое.
- Вопрос консолидации записать в `snapshot.md` → «Не проверено» и в `backlog.md`,
  чтобы следующая сессия не начинала слияние молча.
- Если каталог читает **код** (например, `docs/prompts/` грузится приложением) — переносить
  нельзя, это не документация, а данные.

### `.gitignore`, закрывающий зеркала

`.claude/` целиком в `.gitignore` — зеркала скиллов и хуки не попадут в коммит.
Правило вида `.claude/` не даёт переоткрыть вложенное: нужен `.claude/*` плюс
`!.claude/skills/` и `!.claude/hooks/`. Сказать пользователю и предложить эти строки;
`.gitignore` — `once`, самому не менять.

### Имена, которые уже заняты

Файл стартера дублирует проектный аналог под другим именем (`guides/operations.md` против
проектного `guides/deploy-and-ops.md`) — не заводить второй документ о том же. Оставить
проектный, добавить указатель в `index.md` и сказать пользователю о расхождении имён.

### Запуск пакетом

- По проекту — ветка `starter-upgrade-<версия>` как точка ревью, один коммит.
- Чужие незакоммиченные файлы в рабочем дереве **не стейджить**: коммитить только своё
  (`git add` по списку, не `-A`).
- `push` и `merge` — человеком. Во многих проектах push в `main` = деплой.

## Чего не делать

- Не возвращать `once`-файлы: `setup-checklist.md` удалён по замыслу, `snapshot.md`
  и `operations.md` — проектные с первого дня, даже если в шаблоне они изменились.
- Не «улучшать» проектные файлы попутно. Обновление стартера — отдельный коммит
  с понятным сообщением, чтобы его можно было откатить одним `revert`.
- Не применять `mixed` целиком, даже если diff выглядит безобидно.
- Не заводить `docs/handoff-*.md` при наличии `agent_docs/`: роль handoff играет
  `agent_docs/snapshot.md`, второе хранилище состояния — та же грабля, что и чужой фреймворк.
- **Никаких symlink в репозитории**: Portainer не клонирует такой репозиторий, деплой стека
  падает и чинится только руками на сервере. Зеркала скиллов — копии
  (`agent_docs/guides/autodeploy.md`, раздел «Грабли»).

## Если в проекте нет `STARTER_VERSION`

Проект создан до введения версий. Сверка всё равно работает — скрипт покажет всё как
«НОВЫЙ»/«ИЗМЕНЁН». Применять по тем же правилам, после чего создать `STARTER_VERSION`.
