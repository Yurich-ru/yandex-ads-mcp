# Автодеплой: стандарт (GitHub → Portainer)

Единый способ доставки кода в бой для проектов сети. Конкретика проекта (имена контейнеров,
адреса, команды) — в `agent_docs/guides/operations.md`; здесь — **стандарт и как его включить**.

## Принцип

**Push в `main` = деплой.** Промежуточных ручных шагов нет, обратимость — новым коммитом.
Единственный гейт — зелёный CI: красный код до прода не доезжает.

```
git push origin main
   ↓  .github/workflows/deploy.yml, job test
тесты/линт (гейт)
   ↓  job deploy (needs: test)
POST $PORTAINER_WEBHOOK_URL  → Portainer ПЕРЕСОБИРАЕТ стек из git
   ↓  пауза
health-гейт по SSH: контейнер running (+ health-эндпоинт) → зачистка старых образов
```

- Коммиты только с документацией и служебными файлами стартера деплой не запускают: их отсекает
  `paths-ignore` в `deploy.yml`. `[skip ci]` в сообщении коммита пропускает и тесты, и деплой —
  для прочих правок, не меняющих образ.
- Миграции/сборку применяет контейнер на старте (entrypoint), отдельного шага в CI нет:
  **миграция едет вместе с кодом** — значит только add-only (см. INV о деструктивных миграциях).
- Один Dockerfile на все роли сервиса; роль выбирается переменной `ROLE` в entrypoint.

## Соглашения (нарушение = сломанный деплой)

| Правило | Почему |
|---|---|
| Имя стека = короткое имя проекта; контейнеры `<стек>-<роль>` | предсказуемость для health-гейта и зачистки образов (фильтр по метке compose-проекта) |
| **Новому сервису НЕ давать свой `build:`** — переиспользовать уже собираемый образ (`image: <проект>-<основной сервис>:latest`) + свой `ROLE` | иначе compose назовёт образ `<проект>-<сервис>`, которого нет в реестре, и любой pull-путь падает `pull access denied` |
| **Не ставить `depends_on: <svc>: condition: service_healthy`** | вместе с новым healthcheck ломает webhook-redeploy стека (webhook принят, стек не обновляется). Делать сервис устойчивым ретраем |
| Каждую переменную окружения **явно прописать** в нужном сервисе compose (`- VAR=${VAR:-}`) | панель подставляет значение только туда, где переменная перечислена; иначе внутри контейнера пусто |
| Производные значения (URL БД из пароля и т.п.) собирать в compose, а не задавать в env стека | два источника истины расходятся молча |
| `mem_limit` на каждый контейнер | один сервис не должен съесть хост |
| **`timeout-minutes` на каждой джобе** любого workflow | без него зависшая джоба крутится 360 минут дефолта GitHub. Минуты Actions общие на организацию, поэтому одна такая джоба останавливает выкаты всех проектов сразу (см. журнал грабель) |
| Мелкие проверки — **шагами одной джобы**, а не отдельными джобами | биллинг Actions считает каждую джобу отдельно и округляет вверх до минуты: проверка на пять секунд стоит столько же, сколько минутная |
| **Не делать отдельной джобой то, что можно сделать шагом деплоя** (пример: `update-version` в rop и bablo — запись версии отдельной джобой перед деплоем) | та же минута округления на каждый push плюс второй checkout и второй старт раннера; если шагу нужны права или секреты деплоя — дать их джобе деплоя, а не заводить ради него свою |
| **Не деплоить на коммиты только с документацией**: `paths-ignore` в `deploy.yml` с полным списком служебных путей стартера (см. ниже) | правка `agent_docs/` или `AGENTS.md` образ не меняет, а пересборка стека стоит минут Actions и перезапуска сервиса впустую |
| **Не ждать фиксированным `sleep`** — опрос с ранним выходом и потолком | `sleep 60` берёт минуту всегда, даже когда стек поднялся за десять секунд, и не спасает, когда он поднимается дольше. Опрашивать раз в 5–10 секунд признак нового стека (health-эндпоинт отдаёт новую версию, `StartedAt` контейнера позже вебхука) и выходить, как только он есть; потолок опроса держать меньше `timeout-minutes` джобы и `command_timeout` ssh-action (10 минут по умолчанию) |

Список `paths-ignore` для деплоя (разбор расхода Actions, 04.10.2026; так стоит в `deploy.yml` стартера):

```yaml
on:
  push:
    branches: [main]
    paths-ignore:
      - '**/*.md'
      - 'agent_docs/**'
      - '.agents/**'
      - '.claude/**'
      - '.codex/**'
      - '.cursor/**'
      - '.cursorignore'
      - '.editorconfig'
      - '.markdownlint.json'
      - '.github/workflows/markdownlint.yml'
      - 'STARTER_VERSION'
      - 'STARTER_MANIFEST'
```

Если `Dockerfile` проекта копирует что-то из этого списка (например, отдаёт `README.md` или
`agent_docs/` как страницы) — этот путь из `paths-ignore` убрать. Коммит, где вместе с
документацией меняется хоть один другой файл, деплой запускает как обычно.

Линт документов (`markdownlint.yml`) идёт только на PR и вручную, не на push: на push каждая
правка документов стоила минуту, а в rop, bablo и cmit-ru-next линт месяцами стоял красным
незамеченным (04.10.2026). Проверять перед push локально:
`npx markdownlint-cli2 AGENTS.md 'agent_docs/**/*.md' '.agents/**/*.md'`.

## Бюджет Actions: проверки не на push-CI, лимит — не авария

Минуты Actions — **одна квота на всех** (организация `cmit-ru` и личный аккаунт — по 2000 минут в месяц на
приватные репозитории, бюджет $0 со стопом и пополняться не будет). Кончились — до 1-го числа не стартует
ни один workflow ни в одном проекте владельца. 18.11.2026 так встали все проекты `cmit-ru`: шесть
параллельных сессий агентов в `erp` за сутки сделали сотни push, на каждый — тесты в пять джоб,
1465 минут за день (разбор — скилл `gh-budget`, история 2026-11-19).

**Что можно в CI на push:** только выкладка — одной джобой с `timeout-minutes`: вызов вебхука и опрос
`/health`. Обычный push в `main` должен стоить 1–3 минуты.

**Чего нельзя в CI на push:** полный прогон тестов, матрицы и шарды, линт отдельной джобой. Тесты —
локально или на своей машине для проверок (так сделано в `erp`: ВМ `erp-ci`, `scripts/remote.sh`), а в CI —
только `workflow_dispatch` или PR.

**Несколько сессий в одном репо** — push-CI не выживает при любой настройке. Проверки на своей стороне,
push пачкой после зелёных проверок, выкладка — передвинуть ветку стека на проверенный SHA и вызвать
вебхук (паттерн ветки `deploy` в `erp`).

**Порог тревоги:** больше 100 минут у одной репы за сутки или 50 % квоты до середины месяца — уже
авария, разбираться сразу. Сторож `gh-budget-watch` (скилл `gh-budget`) проверяет это каждый час и
шлёт тревогу в Telegram; автовыключатель может сам выключить Actions у репы-виновника.

**Упёрлись в лимит — проект сам переходит на выкладку без Actions, ни у кого не спрашивая:**
проверки локально или на своей ВМ → push → `curl -fsS -X POST "$(cat ~/.config/<проект>/portainer-webhook)"`
(файл 0600 кладёт инфраструктура, адрес не печатать) → опрос `/health` с новой версией. Если образ
собирается в CI и пушится в реестр (а не собирается Portainer из git) — собрать и запушить его
вручную тем же Dockerfile. С 1-го числа CI снова работает сам, возвращать ничего не нужно.

**Webhook СОБИРАЕТ, кнопка «Pull and redeploy» ПУЛЛИТ.** Кнопку в UI не нажимать: наши образы
собираются локально и в реестр не пушатся. Деплой — только через webhook (его зовёт CI).

## Что нужно настроить один раз

### 1. GitHub (агент может сам, если есть `gh`)

| Что | Имя | Значение |
|---|---|---|
| Секрет | `PORTAINER_WEBHOOK_URL` | URL вебхука стека (см. шаг 2) |
| Секрет | `SSH_HOST` / `SSH_USER` / `SSH_KEY` | доступ к хосту для health-гейта |
| Переменная | `DEPLOY_ENABLED` | `true` — включает деплой |
| Переменная | `SSH_CHECK_ENABLED` | `true` — включает пост-деплой проверку |
| Переменная | `HEALTH_CONTAINER` / `STACK_NAME` | имя контейнера для проверки / имя стека |

```bash
gh secret set PORTAINER_WEBHOOK_URL --repo <owner>/<repo> --body "https://<portainer>/api/stacks/webhooks/<uuid>"
# Переменные: в старом gh нет `gh variable` — через API:
gh api -X POST repos/<owner>/<repo>/actions/variables -f name=DEPLOY_ENABLED -f value=true
gh api repos/<owner>/<repo>/actions/variables --jq '.variables[] | "\(.name)=\(.value)"'   # проверка
gh api -X PATCH repos/<owner>/<repo>/actions/variables/DEPLOY_ENABLED \
  -f name=DEPLOY_ENABLED -f value=true                                  # переключить уже созданную
# Многострочный секрет (приватный ключ) — только перенаправлением stdin:
gh secret set SSH_KEY --repo <owner>/<repo> < ~/.ssh/<key>
```

> Грабля: `gh secret set X --body -` записывает **литерал `-`**, а не stdin, а `--body-file`
> в gh 2.4.0 (версия в dev-контейнере) ещё нет. Однострочное значение передавать как
> `--body "..."`, многострочное — перенаправлением `< файл`; затем проверять реальным вызовом.
>
> Грабля: в gh 2.4.0 у `gh run view` нет полей `--json jobs` и у `gh repo view` нет
> `--json visibility`. Состояние job'ов смотреть через
> `gh api repos/<owner>/<repo>/actions/runs/<id>/jobs`.

### 2. Portainer (агент может сам — нужен API-токен)

Токен: в Portainer → *My account* → *Access tokens* → *Add access token* (значение показывается
один раз). Дальше все вызовы с заголовком **`X-API-Key: <token>`**.

> Токен = управление контейнерами хоста. Хранить вне репозиториев (например,
> `~/.config/cmit/deploy.env`), никогда не коммитить, при подозрении — отозвать в UI одним кликом.
> По возможности — отдельный пользователь Portainer с правами только на нужное окружение
> (права токена = права его пользователя).

```bash
source ~/.config/cmit/deploy.env      # PORTAINER_URL, PORTAINER_API_TOKEN
H="X-API-Key: $PORTAINER_API_TOKEN"

curl -s -H "$H" "$PORTAINER_URL/api/endpoints" | jq '.[] | {Id, Name}'        # → endpointId
curl -s -H "$H" "$PORTAINER_URL/api/stacks"    | jq '.[] | {Id, Name, AutoUpdate}'
# Создание стека из git: POST /api/stacks/create/standalone/repository?endpointId=<N>
#   тело: имя стека, URL репозитория, ветка, путь к compose, env-переменные, autoUpdate(webhook),
#   для приватного репо — учётные данные git.
# Точные поля тела сверять со swagger своей версии Portainer (у инстанса /api/docs может не быть;
# версия — GET /api/system/status, публичный).
```

Webhook стека: UUID лежит в поле `AutoUpdate.Webhook`, полный URL —
`<PORTAINER_URL>/api/stacks/webhooks/<uuid>`; его и класть в секрет GitHub. Триггер — `POST` на этот URL.

### 3. Остаётся человеку

- Выпуск самого API-токена Portainer (нужен пароль пользователя) и SSH-ключа для health-гейта.
- DNS-запись поддомена и proxy-host + TLS в reverse-proxy (если не автоматизировано отдельно).
- Значения секретов приложения (ключи интеграций) — в env стека.

## Грабли (стоили сломанных деплоев)

### Symlink в репозитории — стек не задеплоится вообще

Portainer клонирует git-стеки через go-git с файловой системой `NoSymlinkFS`: **любой** symlink
в репозитории даёт `repository contains a symlink, which is not allowed for security reasons`.
Отключить нельзя. Классический источник — зеркала скиллов `.claude/skills/<name>`; в стартере они
поэтому обычные копии каталогов.

Хуже самого отказа — след: клон рвётся посреди checkout, и в `/data/compose/<id>` остаётся `.git`
(в норме Portainer удаляет его после клона). Дальше **каждый** вебхук падает уже с
`failed to clone git repository: repository already exists` — даже после того, как symlink из
репозитория убрали.

Лечение:

1. Убрать symlink из репозитория (зеркала — копиями) и запушить.
2. На хосте удалить **только** `.git` стека, рабочее дерево оставить:

   ```bash
   rm -rf /var/lib/docker/volumes/portainer_data/_data/compose/<stack_id>/.git
   ```

3. Повторно дёрнуть вебхук (`POST <PORTAINER_URL>/api/stacks/webhooks/<uuid>`) или
   `gh run rerun` деплойного workflow.

Диагностика — в логах Portainer (через ssh обязательно с `timeout`, чтобы не оставить
осиротевший стрим): `docker logs portainer` → строка `webhook failed to redeploy a stack |
... stack=<name> stack_id=<id>`.

### «Success» при упавшем вебхуке

`POST` на вебхук возвращает успех до того, как Portainer попробует пересобрать стек. Workflow,
который останавливается на «вебхук принят», зелёный при полностью сломанном деплое — так пять
проектов сутки считались задеплоенными. Поэтому пост-деплой гейт (`SSH_CHECK_ENABLED=true`)
обязателен, и проверять он должен **реально новый стек**: `StartedAt` целевого контейнера позже
времени вызова вебхука, а не просто «контейнер running».

### Env стека вебхук не перечитывает

Вебхук обновляет **только** compose из git. Env-переменные стека Portainer хранит у себя,
отдельно от репозитория, и сам их не чистит: переменная, убранная из `docker-compose.prod.yml`,
продолжает раздаваться контейнеру. В коде и в `.env.example` её уже нет, а в `docker inspect`
она есть — 16.09 так нашлись четыре переменные вынесенного сервиса, среди них живой платный
токен, сутки спустя после выноса.

Менять env стека — отдельным вызовом, полным списком (тело заменяет `Env` целиком, PATCH нет):

```bash
curl -s -H "$H" "$PORTAINER_URL/api/stacks/<id>" | jq '.Env'   # взять текущий список
# из него убрать/добавить нужное и отправить обратно:
#   PUT /api/stacks/<id>/git/redeploy?endpointId=<N>
#   тело: env (полный список), prune, а для git-стека ещё
#         repositoryAuthentication: true + repositoryUsername/repositoryPassword
```

Пароль git — из `gh auth git-credential get` (ввод: `protocol=https\nhost=github.com\n\n`),
**не** `gh auth token`: у токена из `gh auth token` может не быть прав на клон приватного репо,
и редеплой упадёт на клоне.

Вызов передеплоивает стек — это перезапуск сервиса, согласовывать с владельцем.
Проверка: `GET /api/stacks/<id>` → в `Env` лишних имён нет; значения при этом не печатать.

### Редеплой через API переписывает git-креды стека

`PUT /api/stacks/<id>/git/redeploy` не просто использует сохранённую авторизацию к репозиторию,
а **перезаписывает её полями тела**. `repositoryAuthentication: false` или поле не передано —
авторизация снимается. Текущий редеплой при этом может пройти, а ломается **следующий** деплой
по вебхуку: приватный репозиторий больше не клонируется, и вскрывается это через день, на чужом
пуше (cmit.ru, 21.09.2026; разрушительный вариант на проде намеренно не воспроизводили).

Надёжно:

- в каждом редеплое через API передавать `repositoryAuthentication: true` вместе с рабочими
  `repositoryUsername`/`repositoryPassword` (PAT, см. выше) — либо `repositoryGitCredentialID`
  сохранённых в Portainer кредов, если стек на них заведён;
- после вызова проверить в ответе, что `GitConfig.Authentication` на месте;
- сначала пуш кода и зелёный вебхук, потом редеплой с env — каждый редеплой это серверный
  билд, а упавший билд сносит работающий стек.

Запрос несёт сразу токен Portainer, PAT и значение секрета, и авторежим Claude Code может его
не пропустить. Запрет не обходить: отдать владельцу готовый блок `KEY=VALUE` для копирования и
попросить вставить в Portainer → стек → Environment variables → **Advanced mode** → Update the
stack. Панель делает тот же редеплой, но креды к репозиторию не трогает.

### Push есть, а прогона нет: кончились минуты Actions

Симптом: коммит в `main` ушёл, во вкладке Actions пусто — ни зелёного, ни красного. Деплой
не «сломался», он не начинался. Минуты Actions — **общая квота организации** (на free-плане
2000 минут в месяц на приватные репозитории), и при бюджете $0 раннеры просто не стартуют.
Публичные репозитории в квоту не входят.

Так 17.09.2026 встали выкаты всех проектов `cmit-ru`: из 2049 израсходованных минут 360 дал
один зависший джоб сборки в приватном форке — дефолтный таймаут GitHub ровно шесть часов, и
`timeout-minutes` в том репозитории не стояло нигде.

Что делать:

- Посмотреть, куда ушли минуты: `gh api /orgs/<org>/settings/billing/actions` (сводка) и
  `gh api /repos/<org>/<repo>/actions/runs --paginate` с полем `run_duration_ms` — по джобам
  видно, кто именно съел квоту.
- Поставить `timeout-minutes` **везде** — это ноль стоимости и страховка от повторения.
- До сброса расчётного периода — **сразу и без вопросов** выкладка без Actions (раздел «Бюджет
  Actions» выше): вебхук Portainer из `~/.config/<проект>/portainer-webhook` (секрет репозитория
  `PORTAINER_WEBHOOK_URL` не читается — адрес даёт инфраструктура из настроек стека). CI-гейта
  при этом нет: проверки гнать самим до push, результат сверять по `/health`.
- Снять блокировку раньше можно только деньгами — ненулевой бюджет Actions на организации.
  Это решение владельца, агент его не принимает.

### Удалённый в git файл остаётся в образе

Копия репозитория у Portainer (`portainer_data/_data/compose/<id стека>`) — не git-клон: при
каждом редеплое файлы добавляются и обновляются, но **не удаляются**. Файл, удалённый или
переименованный в git, остаётся там, и `COPY` в Dockerfile уносит его в образ. Симптом: в
контейнере лежит то, чего в `git ls-files` нет.

Так 20.10.2026 в `news` после переименования промптов `draft.v3.md` → `draft.v4.md` в образе
оказались оба файла, а код брал первый из `glob` — прод несколько минут писал тексты старым
промптом, хотя деплой был зелёным.

Что делать:

- Код не должен зависеть от того, что файла нет: не брать «первый попавшийся» из `glob`, а
  выбирать явно (последнюю версию, точное имя).
- Если старый файл мешает — удалить его в копии Portainer на сервере руками и передеплоить;
  после переименований сверять `ls` в контейнере с `git ls-files`.

## Проверка, что стандарт включён

- [ ] `gh api repos/<owner>/<repo>/actions/variables` показывает `DEPLOY_ENABLED=true`
