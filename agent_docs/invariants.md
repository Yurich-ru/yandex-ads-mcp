# Инварианты продукта

Жёсткие правила продукта, которые нельзя нарушать. Не стиль, не предпочтение — нарушение инварианта = баг.

Отличие от правил в `AGENTS.md`: там — как работает **агент**, здесь — что не должно произойти с **продуктом** (данные, безопасность, контракты).

Если инвариант мешает задаче — это не повод его нарушить, а повод обсудить: либо ослабить формулировку (с записью причины в «История»), либо изменить задачу.

**Категории (подсказка):** `data` · `security` · `api` · `performance` · `migration` · `compatibility` · `pii`

---

## INV-001: Секреты не попадают в git

**Категория:** security
**Правило:** OAuth-токены, Api-Key, Folder ID и реальные логины кабинетов — только в `.env` (gitignored) или в `env` конфига ассистента. В коде, доках, `agent_docs/` и коммитах — только имена переменных и плейсхолдеры. Репозиторий публичный.
**Почему:** Утечка токена даёт полный доступ к рекламному бюджету клиента; удаление из истории постфактум ненадёжно.
**Как проверить:** ревью diff перед коммитом; `.env` в `.gitignore`, `.env.example` без значений.
**История:** —

## INV-002: Токены не пишутся в логи

**Категория:** security / pii
**Правило:** В логи никогда не попадают OAuth/IAM-токены и Api-Key. Тела запросов и ответов пишутся только при `YD_LOG_BODIES=true`; файл лога создаётся только при заданном `YD_LOG_FILE`.
**Почему:** Лог-файл лежит рядом с конфигом ассистента и легко утекает вместе с ним; тела ответов содержат данные кампаний клиентов.
**Как проверить:** `test_safety.py` (проверка, что лог-файл по умолчанию не создаётся); grep кода логирования на `Authorization`.
**История:** —

## INV-003: Защитные режимы — opt-in, дефолт не меняется

**Категория:** compatibility
**Правило:** При пустых `YD_READONLY`, `YD_CONFIRM`, `YD_ALLOWED_LOGINS`, `YD_DIRECT_TOKENS` сервер ведёт себя как базовый MCP-сервер: все инструменты доступны, лишних параметров в схемах нет.
**Почему:** Публичный пакет с внешними пользователями; изменение дефолта ломает чужие конфиги молча.
**Как проверить:** `test_safety.py` — схемы без `confirm` при выключенном `YD_CONFIRM`; ручной прогон с пустым `.env`.
**История:** —

## INV-004: Мутация блокируется до сетевого вызова

**Категория:** security / data
**Правило:** При `YD_READONLY=true` любой изменяющий инструмент (add/update/delete/action/set/…) возвращает отказ **до** HTTP-запроса; при `YD_CONFIRM=true` без `confirm=true` — только превью. Каждый новый инструмент обязан быть правильно классифицирован как mutating или read-only.
**Почему:** Агент, работающий с боевым кабинетом, не должен иметь физической возможности изменить ставки или удалить кампанию по ошибке.
**Как проверить:** `test_safety.py` проверяет классификацию всех инструментов; новый инструмент без классификации — красный тест.
**История:** —

## INV-005: Частичный провал массовой операции не выглядит успехом

**Категория:** api / data
**Правило:** Ответы изменяющих вызовов Директа разбираются на per-item `Errors`/`Warnings` и сводятся в `_partial_success`; инструмент не возвращает «ок», если хотя бы один элемент не применился.
**Почему:** Директ отвечает 200 на пакет, где половина объектов отклонена; без разбора агент отчитается об успехе, а кампания останется наполовину настроенной.
**Как проверить:** `test_safety.py` (annotate_partial); ревью новых мутирующих инструментов Директа на прохождение через `annotate_partial()`.
**История:** —
