# Правила работы над проектом

> Если в репозитории присутствует `agent_docs/setup-checklist.md` — пройти его и удалить.

## Описание проекта

- **Проект:** `yandex-ads-mcp` — MCP-сервер (Python, stdio) для Яндекс Директа (API v5), Яндекс
  Метрики, Яндекс Аудиторий и Wordstat API. 151 инструмент, версия 1.2.0, публичный репозиторий
  на GitHub под лицензией MIT.
- **Цели пользователя/команды:** управлять рекламой, сегментами и аналитикой из AI-ассистентов
  (Claude Code, Cursor, Windsurf), не подвергая боевые кабинеты риску: read-only и confirm-режимы,
  белый список логинов, честный partial-success массовых операций.
- **Как используется:** подключается как stdio MCP-сервер в конфиг ассистента (`mcpServers`);
  один процесс — один набор токенов из переменных окружения. Несколько кабинетов Директа —
  аргументом `client_login` (агентский `Client-Login` или свой токен из `YD_DIRECT_TOKENS`).
- **Контекст и ограничения:** Python ≥ 3.10, зависимости только `mcp<2` и `httpx`. Код —
  `server.py` (конфиг, защитная обвязка, инструменты Директа и Wordstat, точка входа) плюс модули
  `tools_metrika.py`, `tools_audience.py`, `tools_direct_extra.py`. Внешние API: Direct v5,
  Metrika, Audience, Yandex Cloud Search API (Wordstat) и IAM. Единственный автотест —
  офлайн `test_safety.py`, CI гоняет его на push/PR в `master`. Есть внешние контрибьюторы.

## Правила проекта

- **Репозиторий публичный.** В код, доки и `agent_docs/` не попадают реальные логины кабинетов,
  токены, Folder ID и имена клиентов — только имена переменных и плейсхолдеры.
- **Защита — opt-in.** С пустыми `YD_READONLY`/`YD_CONFIRM`/`YD_ALLOWED_LOGINS` поведение
  не меняется. Новая защитная логика не должна ломать дефолт.
- **Релиз = три места:** версия в `pyproject.toml`, запись с датой в `CHANGELOG.md`, версия
  в скобках в сообщении коммита («… (1.2.0)»). Основная ветка — `master`, не `main`.
- **Новый инструмент:** добавить в таблицу «Возможности» и в «Полный список инструментов»
  README, поправить счётчик в docstring `server.py`; убедиться, что классификация
  mutating/read-only и Direct/не-Direct корректна — это проверяет `test_safety.py`.
- **Новая переменная окружения:** строка в таблице README «Переменные окружения»
  и в `.env.example`.
- **Логи:** токены не логируются никогда; тела запросов — только при `YD_LOG_BODIES=true`;
  файл лога — только при заданном `YD_LOG_FILE`.
- **Перед коммитом:** `python3 test_safety.py` зелёный (офлайн, токены не нужны).

## Принципы работы агента

> Эти принципы смещают баланс в сторону точности и минимализма за счёт скорости. Для тривиальных задач — здравый смысл.

### 1. Понять до начала действий

**Не додумывай. Не скрывай неуверенность. Озвучивай компромиссы.**

- Явно проговори допущения перед началом.
- Если задача допускает несколько прочтений — перечисли их и выбери самостоятельно с кратким обоснованием. Не выбирай молча.
- Если есть более простой путь — скажи об этом. Возражай аргументированно.
- Если что-то непонятно — остановись, назови что именно непонятно, спроси.

Формат вопросов: коротко и по делу. Контекст вопроса прикладывать отдельно (списком ссылок/цитат), чтобы пользователь мог ознакомиться при необходимости.

### 2. Минимум необходимого

**Минимальный объём решения, ничего спекулятивного.**

- Никаких возможностей сверх того, что просили.
- Никаких абстракций для одноразового результата.
- Никакой «гибкости» и «конфигурируемости», которые не запрашивались.
- Никакой защиты от сценариев, которые не могут произойти.
- Если получилось много, а можно было меньше — переделай.

Тест: сказал бы опытный коллега, что это переусложнено? Если да — упрости.

### 3. Точечные изменения

**Касайся только того, что нужно. Убирай за собой только своё.**

- Не «улучшай» соседний материал, форматирование, формулировки.
- Не пересобирай то, что не сломано.
- Подстраивайся под существующий стиль, даже если сделал бы иначе.
- Если заметил несвязанное «мёртвое» — упомяни, не удаляй.
- Удаляй только то, что ТВОИ правки сделали ненужным. Чужое «мёртвое» не трогать.

Критерий: каждое изменение должно прослеживаться к запросу пользователя.

### 4. Работа от проверяемой цели

**Сформулируй критерий успеха. Доводи до проверки.**

Преобразуй задачу в проверяемую цель:

- «Добавить раздел» → «Описать, что должно появиться; убедиться, что оно есть и связано с остальным».
- «Починить баг» → «Воспроизвести шагами; убедиться, что воспроизведение перестаёт работать».
- «Привести в порядок» → «Зафиксировать состояние до; убедиться, что критерий после выполнен».

Многошаговые задачи — короткий план с проверками:

1. [Шаг] → проверка: [как убедиться]
2. [Шаг] → проверка: [как убедиться]

Сильные критерии успеха позволяют работать автономно.

## Автономность

- Работать самостоятельно и доводить задачу до конца.
- Не запрашивать согласование на рутинные решения. Согласование — только перед необратимыми действиями или действиями, влияющими на shared систему.
- При нехватке контекста — сначала вывести из имеющихся артефактов; если действительно не хватает — задать 1–2 коротких вопроса с приложенным контекстом отдельно.

## Назначение AGENTS.md и границы

- AGENTS.md содержит только универсальные правила, применимые ко всем задачам в проекте.
- Специфические инструкции — в `agent_docs/`; не раздувать AGENTS.md.
- Все проектные документы — в `agent_docs/`, кроме `README.md`, `AGENTS.md`, `CLAUDE.md`.
- Событийные документы вести атомарно: одна итерация, решение, проверка или отчёт — один файл по правилам `agent_docs/guides/atomic-documents.md`.

## Версия стартера и обновление

Проект создан из `cmit-ru/cmit-starter`; версия шаблона — в `STARTER_VERSION`, граница между
шаблонным и проектным — в `STARTER_MANIFEST`. Улучшения стартера в проект сами не приезжают:
подтягивать скиллом `/starter-upgrade` (показывает diff по границе, применять по категориям).
Обратный поток — улучшения, найденные в проекте и общие для всех, — коммитить в стартер.

## Project-Local Skills

- Если проекту нужны локальные skills, источник истины: `.agents/skills/<name>/SKILL.md`.
- Platform mirrors: `.claude/skills/<name>`, `.codex/skills/<name>`, `.cursor/skills/<name>` должны быть symlink на `../../.agents/skills/<name>`.
- Skill metadata должна показывать ту же slash-команду, которую вызывает пользователь: `name: <command>`, description начинается с `/<command>`, первый H1 — `# /<command>`, `agents/openai.yaml display_name: "/<command>"`.
- Не создавать новые slash-command файлы; полезные workflows оформлять как skills.
- Manifest всегда называется `SKILL.md`.

## Память проекта: контракты и состояние

Память живёт на двух осях; при старте сессии читать обе, при завершении — обновлять state.

**Контракты — что должно быть (меняется медленно):**

- `agent_docs/architecture.md` — карта системы.
- `agent_docs/invariants.md` — жёсткие правила продукта; нарушение инварианта = баг, а не вкусовщина. Если инвариант мешает задаче — обсуждать, а не нарушать.
- `agent_docs/adr/` — журнал значимых решений.

**State — что есть сейчас (меняется быстро):**

- `agent_docs/snapshot.md` — текущая точка работы: что в процессе, что блокирует, следующие шаги.
- `agent_docs/backlog.md` — план: Next / Soon / Later / Won't do.

**Операции — как это запустить и эксплуатировать (пополняется по мере набивания шишек):**

- `agent_docs/guides/operations.md` — запуск, тесты, деплой, секреты, доступ к проду и журнал
  инфраструктурных грабель. Всё, что нельзя вывести из кода. Заполнять при первом запуске/деплое
  и **каждый раз, когда разгадывание инфраструктуры заняло больше пары минут**.

### Знание: куда что писать

У агента может быть своя память (личные заметки платформы, автопамять). Она **привязана к машине
и пользователю** и не переезжает: другая сессия на другом компьютере, другой участник команды и CI
её не увидят. Поэтому выбор хранилища определяется не тем, «важно ли это», а тем, **чьё это
свойство**.

| чьё свойство | пример | куда |
|---|---|---|
| **репозитория** | как запускать тесты этого проекта; почему выбрана эта схема БД | `agent_docs/` — `operations.md`, `adr/`, `snapshot.md` |
| **машины и инфраструктуры** | `docker logs` через ssh оборачивать в `timeout`; где живёт Portainer; версия `gh` в контейнере | **стартер** (`agent_docs/guides/`, приезжает в каждый новый проект) или глобальный `CLAUDE.md` |
| **пользователя** | предпочтения, стиль, указатели на файлы | приватная память агента |

Проверочные вопросы перед сохранением:

- *«Увидит ли это новая сессия на чужой машине, если знание нужно для работы над проектом?»*
  Если нет — знание не сохранено, а потеряно.
- *«Относится ли это к одному репозиторию или ко всем нашим проектам сразу?»* Если ко всем —
  в `operations.md` одного проекта оно осядет и остальные его не увидят. Место такому знанию —
  стартер: он уже носитель общего знания (стандарт автодеплоя в `guides/autodeploy.md` — про
  инфраструктуру организации, а не про какой-то проект).

Типичный случай утечки: агент полчаса разбирался, почему падает деплой, разобрался — и записал
вывод «себе», потому что это «не фича и не решение». Место такому знанию — `operations.md`
(журнал грабель), а если грабля общая для всех проектов — гайд в стартере.

**Память и репозиторий расходятся — прав репозиторий.** Приватная память грузится автоматически
и читается авторитетно, поэтому протухшая запись в ней хуже, чем её отсутствие. В памяти держать
только адреса и предпочтения, не факты, живущие в репозитории; указатель на файл перед действием
проверять — файл мог переехать.

## При начале работы

- Свериться с разделом «Описание проекта» выше — это основной контекст.
- Прочитать `agent_docs/snapshot.md` и `agent_docs/backlog.md` — текущее состояние и план.
- Перед запуском, деплоем или отладкой окружения — прочитать `agent_docs/guides/operations.md`
  (там команды и уже известные грабли; не переоткрывать их вслепую).
- Открыть `agent_docs/development-history/README.md` и самостоятельно определить релевантную глубину просмотра записей по риску задачи, затронутым файлам и необходимости восстановить контекст.
- По карте `agent_docs/index.md` открыть только релевантные файлы.
- При проектной терминологии — свериться с `agent_docs/glossary.md`.

## Универсальные правила

- Следовать существующим паттернам и соглашениям проекта.
- **В интерфейсах — язык пользователя, не разработчика.** Перед добавлением любого видимого
  текста (кнопка, заголовок, пункт меню, статус, текст ошибки) проверить: поймёт ли его тот, для
  кого система сделана, без объяснений? Технические заимствования («провижининг», «тенант»,
  «скоуп», «грант», «токен», «retry») в видимых текстах заменять понятными словами. Идентификаторы
  в коде, URL и комментарии — можно техническими: правило только про то, что читают люди.
- Не использовать AGENTS.md как стайлгайд или справочник команд; для стиля — линтеры, форматтеры и существующие артефакты.
- Документы держать краткими; вместо копирования больших фрагментов — ссылаться на файлы и разделы.
- Обновлять затронутую документацию.
- Сессию не тянуть до предела контекста: закрыл задачу — `/handoff`, затем `/clear`.
  `/compact` оставляет около 1,7% контекста и стоит минуты, поэтому он исключение,
  а не режим по умолчанию — см. `agent_docs/guides/context-management.md`.

## Чек-лист перед завершением задачи

- Требования выполнены, результат соответствует ожидаемому поведению.
- Ни один инвариант из `agent_docs/invariants.md` не нарушен.
- Обновлены `agent_docs/snapshot.md` (текущая точка) и при необходимости `agent_docs/backlog.md`.
  Готовый порядок — скилл `/handoff`.
- Каждое изменение прослеживается к исходному запросу (нет «попутных улучшений»).
- Документация обновлена; для нетривиальных изменений — отдельная запись в `agent_docs/development-history/YYYY-MM-DD-HHMM-title.md`.
- Если по ходу задачи выяснилось что-то про запуск, деплой, окружение, секреты или прод (особенно
  если на разгадывание ушло время) — записано в `agent_docs/guides/operations.md`, а не в приватную
  память агента.
- Если принято важное решение — добавлена отдельная запись в `agent_docs/adr/YYYY-MM-DD-HHMM-title.md` (шаблон: `agent_docs/templates/adr.md`).
- Сверено с `agent_docs/guides/dod.md`, критерии DoD выполнены или зафиксированы причины отклонений.
- Если тесты применимы и не запускались/не добавлены — указано почему.

## Признаки того, что правила работают

- Меньше лишних правок в diff'ах и материалах.
- Меньше переделок из-за переусложнения.
- Уточняющие вопросы — до начала, а не после ошибок.
